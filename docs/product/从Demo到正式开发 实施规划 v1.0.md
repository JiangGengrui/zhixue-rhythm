## 0. 先决策：三条技术路线

现有资产是**纯静态 Web（HTML/CSS/JS + WorkBuddy 云数据库）**；架构文档写的是 **Flutter 双端 + Go 模块化单体 + Postgres + 同步协议**。两者不能直接对接，必须先选路线，否则后续工作会返工。

| 路线 | 形态 | 复用现有 demo | 4 周可验证 | 主要风险 |
|---|---|---|---|---|
| **A. 按架构文档原样走** | Flutter App + Go 后端 + 小程序 | 仅设计参考，UI 需重写 | ❌ 不现实 | 三端并行，人力不够 |
| **B. Web 先行（推荐）** | React/TS PWA + Go 后端 + IndexedDB | UI/交互复用 ~80% | ✅ | 需补本地库与同步 |
| **C. 继续纯静态 + 云数据库** | 静态页 + PostgREST | 100% 复用 | ✅ 最快 | 无服务端事务/定时任务，跑不动排程与重排引擎 |

**建议选 B**：前端保留现有视觉与动效资产，重写为组件化 Web 应用；后端按架构文档实现 Go 的 `api` + `planner` 两个入口与核心引擎；同步先用「服务端为准 + 操作队列」的简化版，`drift` 换成 IndexedDB。
**若必须 4 周上线**，则限定范围：只做「建目标 → 自动拆解 → 排本周 → 每日打卡 → 周报」一条链路，砍掉重排、多端、小程序。

## 1. 整体目标与范围

### 1.1 产品目标（V1）
让长期学习者在 3 分钟内完成「目标 → 本周 → 今天」的落地，并在执行偏离计划时获得一条可执行的调整建议，而不是自责。

### 1.2 V1 范围（In / Out）

**In（必须真实可用）**
- 账号：注册/登录/登出、会话保持、单用户数据隔离
- 目标：创建、可行性评估（R 值真实计算）、阶段与里程碑
- 拆解：目标 → 阶段 → 计划项（节点/工时/权重）
- 排程：按周可用时段装箱，生成 Block，容量校验与弹性位
- 执行：打卡（开始/暂停/完成/跳过）、实际用时记录、中断后继续
- 复盘：达成率、有效时长、估时偏差、归因，全部由数据算出
- 数据：导出、删除账号与数据
- 运营：留言审核与删除、表单限流

**Out（V1 不做）**
- 自动重排四级策略（V1.1，先保留"手动挪动 + 提示"）
- 多端同步与离线冲突合并（V1 用服务端为准）
- 小程序、订阅消息、支付、社交/组队

### 1.3 成功判据
D7 留存 ≥ 25%；周计划完成率 ≥ 55%；周报打开率 ≥ 60%；估时偏差 MAE 逐周下降；LCP < 2.5s。

## 3. 必须补齐的核心功能（Demo 里"看起来有、实际没有"）

1. **打卡状态机**：`pending → running → done / skipped / abandoned`，记录 `started_at / ended_at / actual_minutes`；支持撤销与补录，非法迁移在服务端拒绝（不是前端隐藏按钮）。
2. **容量与排程引擎**：输入周可用分钟 + 计划项工时，输出 Block 列表；装不下时给出「移入弹性位 / 顺延次日 / 砍低优先级」三选一，并说明影响。**必须纯函数、可单测、确定性**（同输入同输出，不读时钟）。
3. **可行性评估（R 值）**：`R = 需求工时 / 可用工时`，可用工时按 0.85 折扣；替换写死的 1.15，并给出"可行/偏紧/不可行"三档与建议。
4. **复盘计算**：达成率（done / planned）、有效时长（Σ session）、估时偏差（中位数 + P90，避免均值被极端值带偏）、归因（容量不足 / 执行中断 / 估时偏低，按规则判定并给出证据句）。
5. **身份与隔离**：所有业务表带 `user_id`，RLS 或服务端强制过滤；会话过期、换设备、登出后清除本地缓存。
6. **留言治理**：长度/频率限制、敏感词、管理员删除；数据库层面留 `deleted_at`（软删），不做物理删。
7. **数据权利**：导出全部个人数据；删除账号时级联清理并在 30 天内彻底移除。

## 4. 边界情况清单（每条都要有明确行为）

**时间**
- 跨零点任务（22:30 开始 01:00 结束）→ 归入开始日，时长按分钟累加
- 用户改时区 / 夏令时 → 按用户时区计算"今天"，服务端存 UTC
- 周起始日可配置（周一/周日），切换后历史周报不重算
- 未来日期打卡、结束时间早于开始时间 → 拒绝并提示

**容量与数据**
- 新用户空状态：无目标、无任务、新一周未规划 → 各有引导文案与一键模板
- 周报除零（当周无计划）→ 显示"本周未规划"而非 NaN
- 估时为 0、负数、超 24h → 校验拦截
- 单日可用时段为 0 或全部被占用 → 排程给出明确原因

**并发与网络**
- 双击打卡、双开页面 → 用 `op_id` 幂等，重复请求返回成功不重复计数
- 提交超时 → 指数退避重试（1/2/4/8s，上限 5 次），失败进入待同步队列
- 离线执行打卡 → 先写本地，恢复后按顺序上行
- 401/403/422/5xx 分类提示，禁止统一"操作失败"

**内容与安全**
- 留言超长/空白/纯表情 → 前后端双校验
- XSS：前端一律 `textContent` 渲染，禁止拼 HTML
- 刷屏 → 同 IP/同设备 1 分钟内 ≤ 3 条

**设备与可访问性**
- ≤560px 关闭 3D 场景，动效降级；`prefers-reduced-motion` 全关
- 键盘可达：所有操作可 Tab 到达、Enter/Space 触发、焦点可见
- 读屏：表单有 label、状态变化有 `aria-live`

## 5. 代码结构与工程配置

### 5.1 仓库结构（对齐架构文档的模块化单体）

```
zhixue/
├── backend/
│   ├── cmd/api/            # HTTP 入口
│   ├── cmd/planner/        # 排程 worker
│   ├── internal/
│   │   ├── identity/       # 账号、会话
│   │   ├── plan/           # 目标、阶段、计划项
│   │   ├── schedule/       # Block、容量、排程调用
│   │   ├── execution/      # 打卡、session
│   │   ├── insight/        # 复盘、归因、周报
│   │   └── platform/       # db、日志、配置
│   └── pkg/engine/         # 纯函数引擎（不依赖 internal）
├── web/                    # 前端（React + TS + Vite）
│   ├── src/domain/         # 与后端同构的计算（预览用）
│   ├── src/data/           # API client、本地缓存
│   ├── src/ui/             # 组件（迁移现有 styles.css token）
│   ├── src/pages/          # today / goal / week / report
│   └── tests/
├── db/migrations/          # 迁移脚本（只增不改）
└── .github/workflows/      # CI
```

**红线**：`pkg/engine` 不得 import `internal/*`；引擎不读库、不读时钟、不用随机数。这条纪律是引擎可单测、可离线重放的前提。

### 5.2 前端迁移策略（复用现有资产）
- 保留：配色与排版 token（从 `styles.css` 抽出 `tokens.css`）、四视图信息架构、动效参数
- 重写：DOM 拼装改为组件 + 状态驱动；`app.js` 的 267 行逻辑拆为 hooks
- 抽取：主页与 demo 两套重复的动效代码合并为 `motion/` 模块（当前是两份实现）
- 3D 场景（`three-effects.js`）保留但改为按需加载，低端/省流不加载

### 5.3 环境与配置
- 三套环境：`dev` / `staging` / `prod`，端点与公开 key 走 `.env`（VITE_ 前缀），禁止写死在 HTML
- 密钥只存在服务端；前端只有 publishable key
- 数据库迁移用版本化脚本，禁止手工改线上表

### 5.4 工程规范
- `git init` + `main`/`feat/*` 分支 + PR 模板（变更说明、影响面、回滚方式）
- ESLint + Prettier + TypeScript strict；Go 用 `gofmt` + `go-arch-lint`
- 语义化提交；发布打 tag；每次发布留 CHANGELOG
- CI 四道门：lint → typecheck → unit → build；PR 不过不准合并

## 6. 测试与错误处理

### 6.1 测试分层
| 层 | 对象 | 目标 | 工具 |
|---|---|---|---|
| 单元 | `pkg/engine`：可行性、装箱、重排、归因 | 覆盖 ≥ 80%，含边界表 | Go testing |
| 单元 | 前端 `domain/` 计算 | 与后端同输入同输出 | Vitest |
| 组件 | 打卡按钮、表单校验、空状态 | 关键交互可回归 | Testing Library |
| 端到端 | 注册→建目标→排本周→打卡→看周报 | 主链路 1 条 + 失败路径 2 条 | Playwright |
| 非功能 | LCP/CLS/A11y | LCP<2.5s、CLS<0.1、A11y≥90 | Lighthouse CI |

**必测的边界用例**：空数据周报、跨零点任务、容量不足、重复打卡、离线补传、时区切换。

### 6.2 错误处理规范
- 统一错误码：`E1xxx` 参数、`E2xxx` 认证、`E4xxx` 业务冲突、`E5xxx` 服务端
- 前端每类错误给可执行文案（不是"出错了"），并提供请求 ID 便于排查
- 全局错误边界：单个组件崩溃不白屏
- 服务端日志结构化（请求 ID、用户 ID、耗时），敏感字段脱敏

### 6.3 可观测
埋点事件：`goal_created`、`plan_generated`、`task_started`、`task_completed`、`task_skipped`、`report_viewed`、`replan_triggered`。
看板：漏斗（注册→建目标→首周执行）、留存、完成率、偏差趋势。前端错误上报接入 Sentry 类服务。

## 7. 分阶段推进（6 周标准版 / 4 周压缩版）

### M0 · 立项与基线（3 天）
- `git init`、CI 空跑通、环境变量、部署到 staging
- 把当前 demo 打 tag 存档为 `v0-demo`，作为视觉基线
- **交付**：可部署的空壳 + CI 绿 + 技术选型 ADR（含 A/B/C 路线决策）
- **验收**：任何人 clone 后三条命令本地跑起来

### M1 · 数据与身份（第 1–2 周）
- 表结构：`user / goal / stage / plan_item / block / session / insight / feedback`
- 登录注册、会话、RLS/服务端过滤；迁移脚本与 seed
- 今日视图改为**读真实数据（只读）**
- **交付**：数据模型文档 + 迁移脚本 + 登录可用
- **验收**：两个账号互不可见；刷新不丢数据；越权请求返回 403

### M2 · 引擎与排程（第 2–3 周）
- `pkg/engine` 三个纯函数：可行性评估、周装箱、归因
- planner 生成 Block；周视图读 Block
- **交付**：引擎 + 单元测试（≥80%）+ 一页算法说明（输入/输出/参数）
- **验收**：给定固定输入，重放三次结果完全一致；装不下时给出可解释建议

### M3 · 执行闭环（第 3–4 周）
- 打卡状态机 + session + 实际用时 + 补录/撤销 + 幂等
- 周报改为真实计算；目标页 R 值真实
- **交付**：一条可追溯的完整链路（计划 → 执行 → 复盘）
- **验收**：随机 20 条任务跑一遍，任何数字都能点进去看到来源

### M4 · 打磨与可运营（第 5 周）
- 空状态、错误处理、移动端、性能预算、A11y
- 留言审核后台、限流、数据导出
- **交付**：错误码表、空状态清单、Lighthouse 报告
- **验收**：E2E 全绿；Lighthouse 达标；弱网/离线可用

### M5 · 灰度上线（第 6 周）
- 10–20 位种子用户、埋点看板、反馈表、热修与回滚预案
- **交付**：发布手册（含回滚步骤）、埋点字典、首周复盘报告
- **验收**：连续 3 天无 P0 缺陷；能回答"用户卡在哪一步"

**4 周压缩版**：M0 合并进 M1，砍掉 M4 中的运营后台与 P1 项，只保留 M1→M3 主链路 + 一次灰度。

## 9. 风险与待决策

| 风险 | 影响 | 应对 |
|---|---|---|
| 继续在静态页上堆功能 | 技术债指数增长，改一处崩一处 | 立即冻结 demo，新功能一律进新仓库 |
| 3D/动效拖累低端机 | 首屏 3s+ | 按需加载 + 低端机降级开关 |
| 4 周内做三端 | 全部半成品 | 只做 Web，Flutter 延后 |
| 单人开发 | 关键路径阻塞 | 砍 P1，先保主链路 |

**需你拍板的三件事**
1. 路线：B（Web 先行）还是 A（Flutter 为主）？
2. 周期：6 周标准版，还是 4 周压缩版？
3. 范围：周报的"归因"是否 V1 就要真实计算（需要更多数据积累）？
