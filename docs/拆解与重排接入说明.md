# 拆解与重排 · 前端接入说明

给正在重建 UI 的一端：本轮补的是 PRD 8.2（拆解引擎）与 8.4（重排引擎），**引擎在服务端，前端只负责调用与呈现**，不要在页面里重算 R 值或装箱结果（那份算法已经同构打包，页面上再写一遍必然漂移）。

改动文件：

| 层 | 文件 | 说明 |
|---|---|---|
| 引擎 | `src/domain/decompose.ts` | 三段式拆解，纯函数 |
| 引擎 | `src/domain/replan.ts` | 触发检测 + 四级方案，纯函数 |
| 模板 | `src/domain/templates.ts` | 3 套知识域树（考研计算机 / 考公 / 项目导学） |
| 接口 | `server/api.mjs` | 4 个新端点 |
| 契约 | `docs/openapi.yaml` | 已同步 |

## 一、拆解（PRD 8.2）

### 1. 取模板清单

```
GET /api/decompose/templates
→ { templates: [{ key, label, nodeCount, totalMinutes }] }
```

`key` 三选一：`postgrad-cs` / `civil-service` / `project-self`。

### 2. 预览草案（不写库）

```
POST /api/goal/decompose
{ "template": "postgrad-cs" }
```

返回：

```jsonc
{
  "applied": 0,
  "result": {
    "template": "postgrad-cs",
    "verdict": "tight",              // comfortable | reasonable | tight | infeasible
    "ratio": 1.08,                   // R = 需求 / 可用
    "demandMin": 5820,               // 裁剪后的需求工时
    "availableMin": 5380,            // 每周可用 × 剩余周数 × 0.85
    "weeksLeft": 8,
    "stageRatio": [0.45, 0.35, 0.2],
    "stages": [
      { "key": "foundation", "label": "基础", "startDate": "2026-11-09", "endDate": "2026-12-08",
        "minutes": 2640, "milestone": "完成 高等数学、数据结构 的第一轮，正确率 ≥ 60%；阶段末做一次限时自测" }
    ],
    "items": [
      { "key": "m1", "title": "高数 · 极限与一元微分", "subject": "math", "module": "高等数学",
        "estimateMin": 1200, "weight": 5, "stage": "foundation", "nodeIds": ["m1"] }
    ],
    "trimmed": [
      { "id": "x5", "title": "行测 · 常识判断", "minutes": 240, "reason": "low-priority",
        "note": "考频 0.50 / 分值 0.05，优先级最低" }
    ],
    "warnings": ["按当前可用时间裁掉了 3 项、约 12 小时…"]
  }
}
```

**呈现要点**

- `stages` 画成时间轴：`基础 / 强化 / 冲刺` 三段，每段显示区间、工时、里程碑。
- `items` 是草案，按 `stage` 分组展示；用户可增删改后再提交（直接调 `POST /api/items`、`DELETE /api/items/:id`）。
- **`trimmed` 必须显式展示**（PRD：避免隐性欠账）。文案建议「已放弃（可加回）」，每行带 `reason`：
  - `low-priority` 低频低分
  - `mastered` 已有基础
  - `merged` 已并入其他任务
- `warnings` 原样展示，不要吞掉。

### 3. 采纳草案

```
POST /api/goal/decompose
{ "template": "postgrad-cs", "apply": true, "replace": true }
→ { "applied": 18, "result": {...} }
```

- 已有计划项时不传 `replace: true` 会返回 **409 / E4009**——这一条是为了防止误覆盖用户手写的计划。
- 应用会**清空原有计划项与全部任务块**（因为任务块引用的计划项已经不存在）。UI 需要在按钮上明确提示这一点。

## 二、重排（PRD 8.4）

### 1. 取方案（只读）

```
GET /api/plan/replan?week=2026-11-09&manual=1
```

```jsonc
{
  "weekStart": "2026-11-09",
  "replanCount": 0,                  // 本周已重排次数
  "blocked": false,                  // 达到 3 次且仍装不下 → 停止重排
  "calibration": null,               // blocked 时给目标校准建议
  "trigger": {
    "triggered": true, "rescue": false, "backlogMin": 320,
    "reasons": [
      { "code": "low-achievement", "label": "连续两天完成率偏低", "detail": "2026-11-07 40%、2026-11-08 50%，低于 60%" }
    ]
  },
  "options": [
    {
      "key": "defer", "label": "顺延到下周",
      "reason": "把这一周装不下的部分顺延，本周只保留能完成的量",
      "cost": "未来的弹性空间会被挤占，下一周会更紧",
      "summary": { "added": 6, "deferred": 2, "dropped": 0, "deferredMin": 180 },
      "plannedMin": 870, "bufferMin": 90,
      "loadIncreasePct": 12, "feasible": true
    }
  ]
}
```

**四个方案按优先级返回，顺序固定**：`defer` 顺延 → `compress` 压缩 → `substitute` 替代 → `drop` 放弃。

每个方案还带 `applicable`：**当前排布下这个方案用不用得上**。例如本周排的全是核心任务（权重 > 3）时，`compress` 的 `applicable = false`，`reason` 会说明原因——这类方案应该置灰并展示理由，而不是让用户点进去发现"什么都没变"。

**每张方案卡必须展示三样东西**（PRD 硬性要求）：

1. `summary` 变更摘要：新增 X 项 / 延期 Y 项 / 放弃 Z 项
2. `cost` 代价
3. `loadIncreasePct` 未来 7 天负载增幅（> 20 时 `feasible=false`，按钮置灰并说明原因）

### 2. 应用方案

```
POST /api/plan/replan/apply
{ "week": "2026-11-09", "option": "defer" }
→ { applied, summary, replanCount, blocks }
```

副作用（需要在确认弹窗里讲清楚）：

| 方案 | 会改动什么 |
|---|---|
| `defer` | 重写本周未完成的块；装不下的量留在计划项剩余工时里，下周继续 |
| `compress` | 同上，并把权重 ≤ 3 的计划项剩余工时压到 70% |
| `substitute` | 同上，且本周不再排权重 ≤ 2 的计划项（计划项本身不删） |
| `drop` | 同上，并**删除**最低权重的那个计划项（不可撤销，需二次确认） |

### 3. 错误

| 状态 | code | 含义 | UI 处理 |
|---|---|---|---|
| 409 | `E1034` | 顺延/压缩仍装不下 | 引导改选「替代」或「放弃」，或提示延长目标日期 |
| 409 | `E1035` | 本周已重排 3 次仍装不下 | 展示 `calibration`（目标校准建议），不再给重排按钮 |
| 400 | `E1033` | 未知方案 | 属前端 bug，报错即可 |
| 400 | `E1036` | 方案在当前排布下不适用（`applicable = false`） | 按钮本就该置灰，属调用侧漏判 |

---

## 三、界面上的两个状态位

1. **触发提示**：`trigger.reasons` 里每条都有 `label` + `detail`，可直接做成提示条（例：「连续两天完成率偏低 · 11-07 40%、11-08 50%」）。`trigger.rescue = true` 时走挽救模式文案，**不要**用「已断更 X 天」这类惩罚性表达（PRD 9.7 零惩罚回归）。
2. **重排上限**：`blocked = true` 时把重排入口替换为「调整目标」，展示 `calibration`。
